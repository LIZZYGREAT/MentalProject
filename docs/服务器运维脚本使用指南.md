# 服务器运维脚本使用指南

本指南适用于服务器上的 MindFlow 工作区，例如 `/opt/feishu-agent/mindflow`。所有命令均从
`mindflow-bot-runtime` 目录执行，除非另有说明。

```bash
cd /opt/feishu-agent/mindflow/mindflow-bot-runtime
```

脚本默认拒绝脏工作区。更新前应先提交并推送；不要用 `docker compose up --build` 代替部署脚本，
否则镜像 revision 会变成 `development`，验收会拒绝继续。

## 日常更新的标准顺序

```bash
cd /opt/feishu-agent/mindflow/mindflow-bot-runtime

sh ./scripts/status_report.sh
sh ./scripts/pull_latest_code.sh
sh ./scripts/deploy_runtime.sh
sh ./scripts/status_report.sh
```

`pull_latest_code.sh` 仅 fast-forward 拉取当前跟踪分支，不会触碰容器。`deploy_runtime.sh` 会构建
当前 HEAD 的 migrate、bot、admin 镜像，等待 PostgreSQL，执行迁移，重建 Bot/Admin，并检查两者的
运行 revision 与 HEAD 一致。通常不需要在它之前执行 `build_images.sh`。

## 各脚本用途

| 脚本 | 何时使用 | 对运行服务的影响 |
| --- | --- | --- |
| `status_report.sh` | 更新前后、故障初查 | 只读，不重启服务 |
| `pull_latest_code.sh` | 从远程获取当前跟踪分支的新提交 | 不触碰容器 |
| `build_images.sh` | 需要提前把生产镜像构建好、但暂不发布 | 不重启服务 |
| `deploy_runtime.sh` | 发布当前 HEAD | 重建 Bot/Admin，执行迁移 |
| `prepare_acceptance_image.sh` | 全量验收前准备当前 revision 的测试镜像 | 会暂时停止并恢复 Bot/Admin |
| `run_acceptance_tests.sh` | 执行全量隔离库验收 | 测试期间会停止 Bot/Admin，结束后恢复 |
| `run_admin_tests.sh` | 运行 Admin 定向回归 | 不应重启 Bot/Admin |
| `clean_stale_containers.sh` | 手动回收已停止容器、悬空镜像 | 默认不影响运行服务或 BuildKit 缓存 |
| `db_inspect.sh` | 只读查看生产数据库状态 | 只读查询 PostgreSQL |

## 部署前检查与拉取

先执行状态报告：

```bash
sh ./scripts/status_report.sh
```

报告会汇总服务器资源、Git 分支和 HEAD、Compose 服务、Bot/Admin revision、迁移状态、PostgreSQL
健康状况与 Docker 磁盘占用。若提示 working tree dirty，先处理服务器上的未提交改动，不要继续部署。

确认当前跟踪分支正确后拉取：

```bash
sh ./scripts/pull_latest_code.sh
```

该脚本只允许 fast-forward；若远程历史分叉，会停止并保留现场，需先人工确认分支策略。

## 发布 Bot 与 Admin

```bash
sh ./scripts/deploy_runtime.sh
```

成功时末尾会显示 `deployed revision <HEAD>`。随后再执行一次状态报告即可确认运行服务、迁移和
revision 都已对齐。

如需在低峰期预构建、稍后再发布，可先执行：

```bash
sh ./scripts/build_images.sh
```

之后仍应执行 `deploy_runtime.sh` 才会迁移数据库并将镜像应用到 Bot/Admin；第二次构建应命中缓存。

## 全量 Acceptance 验收

前置条件：

- `mindflow-bot-runtime/.env` 存在且包含 `MINDFLOW_TEST_POSTGRES_URL`；
- 该 URL 指向独立、允许清空的库，库名只能是 `mindflow_acceptance_test` 或 `mindflow_test_*`；
- Bot/Admin 已由 `deploy_runtime.sh` 部署到当前 HEAD。

验收脚本会显式把 `.env` 交给 Compose；无需再在主机上手工导出数据库 URL，也不会打印该 URL。

```bash
sh ./scripts/prepare_acceptance_image.sh
sh ./scripts/run_acceptance_tests.sh
sh ./scripts/status_report.sh
```

`prepare_acceptance_image.sh` 将当前 revision 的开发依赖和应用代码烘焙进 `mindflow-acceptance:local`。
`run_acceptance_tests.sh` 只运行测试，不会再次构建镜像或安装 pip 依赖。两个脚本都会因小规格服务器的
资源限制而短暂停止 Bot/Admin；无论成功、失败或中断，脚本都会尝试恢复二者并校验 revision。

## Admin 定向回归

该测试要求 Bot、Admin 已运行，且 Acceptance 镜像已通过 prepare 更新到当前 HEAD：

```bash
sh ./scripts/run_admin_tests.sh
```

运行前建议先完成上述 Acceptance 镜像准备。脚本会检查 Bot/Admin 在测试前后均仍在运行；若容器 ID
变化，会给出警告。

## 缓存与磁盘维护

仅更新业务代码时，Dockerfile 中的 requirements、apt、pip 层应命中缓存；只有代码复制层及其后的
层会重建。首次切换到新的 Dockerfile、requirements 改动、基础镜像变更，或 BuildKit 缓存已被清理时，
重新下载依赖才是预期现象。

`prepare_acceptance_image.sh` 成功后会保留构建缓存，避免下次仅改代码又下载依赖。若构建失败，脚本会
按 `ACCEPTANCE_BUILD_CACHE_KEEP`（默认 `6GB`）兜底裁剪可能残留的失败缓存。

日常回收先预览：

```bash
sh ./scripts/clean_stale_containers.sh --dry-run
```

确认后回收停止的容器和悬空镜像：

```bash
sh ./scripts/clean_stale_containers.sh
```

只有磁盘空间不足时才裁剪 BuildKit 缓存：

```bash
ACCEPTANCE_BUILD_CACHE_KEEP=6GB \
  sh ./scripts/clean_stale_containers.sh --build-cache
```

最后一个命令可能淘汰 pip 下载缓存，使下一次镜像构建重新下载依赖；它不应纳入常规验收流程。不要执行
`docker system prune`，除非已明确接受同时清理未使用 BuildKit 缓存的后果。

## 数据库只读检查

```bash
sh ./scripts/db_inspect.sh summary P002
sh ./scripts/db_inspect.sh tables
sh ./scripts/db_inspect.sh events all 20
```

`db_inspect.sh sql 'SELECT ...'` 仅接受单条 `SELECT` 或 `WITH` 查询，并拒绝数据修改和 DDL。

## 常见排查

- `working tree is dirty`：先查看 `git -C .. status --short`，处理服务器本地改动后重试。
- `acceptance image missing or stale`：先执行 `sh ./scripts/prepare_acceptance_image.sh`。
- 验收测试库被拒绝：检查 `.env` 的 `MINDFLOW_TEST_POSTGRES_URL`，不要使用生产 `DATABASE_URL`。
- 依赖再次下载：先执行 `sh ./scripts/status_report.sh` 查看磁盘占用；再检查近期是否运行过
  `clean_stale_containers.sh --build-cache`、`docker builder prune` 或 `docker system prune`。
