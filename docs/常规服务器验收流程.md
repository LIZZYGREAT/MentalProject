# 常规服务器验收流程

本流程以 Runtime 已提供的脚本为唯一入口，避免手工执行 `git fetch`、`docker compose build`、
迁移和 revision 比对时遗漏步骤。

> 适用目录：`/opt/feishu-agent/mindflow`。开始前确认服务器工作区没有未提交改动，并确认当前跟踪分支就是待发布分支。

## 1. 发布前状态检查

```bash
cd /opt/feishu-agent/mindflow/mindflow-bot-runtime
sh ./scripts/status_report.sh
```

若报告提示工作区脏、Docker/数据库异常或 Bot/Admin revision 与 HEAD 不一致，先处理异常；不要直接继续。

## 2. 拉取当前跟踪分支

```bash
sh ./scripts/pull_latest_code.sh
```

该脚本只允许 fast-forward 拉取，不会重启任何容器。若无新提交会安全退出；若发生分叉，人工确认后再处理。

## 3. 部署当前 HEAD

```bash
sh ./scripts/deploy_runtime.sh
```

脚本会构建 migrate、Bot、Admin 镜像，启动并等待 PostgreSQL，执行 Alembic migration，重建 Bot/Admin，
并验证运行 revision 等于 Git HEAD。不要用 `docker compose up --build` 替代它。

## 4. 全量 Acceptance 测试

确认 `mindflow-bot-runtime/.env` 已配置专用的 `MINDFLOW_TEST_POSTGRES_URL`。该库必须是可清空的隔离库，
数据库名只能为 `mindflow_acceptance_test` 或 `mindflow_test_*`，不得填写生产 `DATABASE_URL`。

```bash
sh ./scripts/prepare_acceptance_image.sh
sh ./scripts/run_acceptance_tests.sh
```

无需手工导出测试数据库 URL：两个脚本会使用 `.env`，且 PostgreSQL guard 会在测试前拒绝空值、生产库或不允许的
主机。准备镜像和全量测试期间，Bot/Admin 会暂时停止以释放小规格服务器资源；脚本在退出时自动尝试恢复服务并检查
其 revision。

## 5. 可选：Admin 定向回归

```bash
sh ./scripts/run_admin_tests.sh
```

此步骤要求 Bot、Admin 保持运行，且第 4 步已准备好当前 revision 的 Acceptance 镜像。

## 6. 最终状态确认

```bash
sh ./scripts/status_report.sh
```

验收通过条件：Bot/Admin revision 都等于 HEAD、数据库位于最新 migration、PostgreSQL 健康，且全量 Acceptance
测试（以及需要时的 Admin 定向回归）返回成功。

## 不属于常规流程的维护操作

需要回收空间时，先预览：

```bash
sh ./scripts/clean_stale_containers.sh --dry-run
```

确认后再执行 `sh ./scripts/clean_stale_containers.sh`。只有磁盘空间不足时才额外使用 `--build-cache`；这会裁剪
BuildKit/pip 缓存，下一次构建可能重新下载依赖。完整说明见[服务器运维脚本使用指南](服务器运维脚本使用指南.md)。
